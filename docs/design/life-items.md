# 生活事項：Bot 怎麼替使用者記住「還有什麼事」

2026-10-31 起草，還沒實作。問題：pi 的 Bot 要用什麼工具，才能把使用者生活上的瑣事管好（求職、財務、繳費、等別人回覆）。開發 pi-mobile 本身的待辦另用 GitHub Issues，不在這裡。

## 現況：兩個真的 Bot 怎麼記事情

2026-10-31 讀了 S24 上兩個每天在用的 Bot（只看結構與數量，內容不寫進這份公開文件）。兩個都選了 Mac mini 當工作的電腦，手機上的共用資料庫（`sql` 工具）是空的，它們沒用到。

**求職管家**：一天三次排程掃職缺，資料在 Mac 上自己的 SQLite（Bot 的記憶寫著這個檔案的位置）。它自己設計了一整套：

| 表 | 用途 | 2026-10-31 的筆數 |
|---|---|---|
| `jobs` | 職缺與狀態（new、considering、applied、interview、waiting_user…） | 1,170 |
| `job_tracking` | 每個在追的職缺：下一步、下一步期限、要不要先問使用者 | 25 |
| `tasks` | 待辦：標題、期限、狀態、連到哪個職缺 | 26（12 筆未完成） |
| `events` | 發生過的事：投遞、收發訊息、排定面試 | 118 |
| `facts` | 長期記住的事：偏好、規則、聯絡方式 | 15 |

**財務管家**：沒有表。每天晚上一個排程彙報一檔 ETF，該注意什麼（例如「跌到某個價位才考慮」）寫在 Bot 的記憶文字裡，每次彙報時自己判斷。

## 看得到的問題

- **期限到了沒人叫**：12 筆未完成的待辦有 3 筆已經過期，5 筆沒有期限。資料庫有 `due`，但沒有任何東西在 due 時叫醒 Bot 或使用者；只有一天三次的掃描順便看到才會提。
- **「下一步」沒有時間**：25 個在追的職缺都寫了下一步，只有 1 個有期限。
- **「等誰」藏在各自的欄位裡**：`waiting_user`、`approval_status` 是求職管家自己發明的；財務管家的「等某個價位」只在記憶文字裡。使用者沒有地方一次看到「現在輪到我的事」。
- **每個 Bot 各記一套、各放一處**：求職在 Mac 的 SQLite，財務在記憶，手機上的資料庫沒人用。換一個 Bot 或換一個模型，就要重新理解那套結構。
- **機密混在資料裡**：求職資料庫的 `facts` 有一筆名稱是 GitHub token 的值，明文存在檔案裡（沒有讀它的值）。機密應該放 pi 的憑證存放處，不該在 Bot 的資料表裡。

## 生活事項有哪幾種

看兩個 Bot 實際記的東西，需要 Bot 再回來處理的事只有三種：

1. **某個時間要做**：期限前回覆、繳費、回診。
2. **在等別人**：等公司回覆面試時間、等退款。等到了要有人知道。
3. **條件成立才要做**：某個價位以下、到某個地點、收到某人的訊息。

三種都需要「到時候自己冒出來」，這是看板做不到的，也是現在缺的。

## 設計：一份手機上的「事項」，Bot 共用

**原則：領域資料留在原地，只把「需要再回來看的事」收成一份。** 求職的職缺、事件紀錄繼續留在它自己的資料庫，那是它的帳本；pi 只多記一份很薄的「事項」，指回帳本裡的那一筆。

**一筆事項的欄位**（少，讓小模型也寫得對）：

| 欄位 | 內容 |
|---|---|
| `title` | 一句話，使用者看得懂 |
| `state` | `todo`（輪到使用者或 Bot 做）／`waiting`（在等別人或某個條件）／`done` |
| `next_at` | 什麼時候再看一次（期限、追蹤日）；沒有就是「不用主動看」 |
| `waiting_on` | 在等誰或什麼（`waiting` 才有）：一個人、一個 app 的訊息、一個條件 |
| `bot` | 負責的 Bot，到時候叫醒它 |
| `ref` | 指回帳本的那一筆（例如求職資料庫的哪個職缺、一個網址），可以沒有 |

- 存在 pi 自己的資料（跟排程一樣是 durable 的文件，只在手機上），不放雲端，也不放使用者的 SQLite（那是給使用者自己的表用的）。
- `state` 是互斥的一個值，不用多個布林欄位湊。

**到時候叫醒**：`next_at` 直接接上排程的精確鬧鐘（跟「等它做完」的 `watch` 同一套）。到了就叫醒負責的 Bot，帶著那筆事項；Bot 照無人值守的規則處理，需要使用者時通知。沒有 `next_at` 的事項不會自己冒出來，所以 Bot 寫事項時要給。

**在等別人**：`waiting_on` 是某個人或 app 時，可以再掛現有的通知事件（`on: notification`，`app`、`contains`）：對方一回就叫醒 Bot，不用等到 `next_at`。

**讓使用者一眼看到**：桌面小工具在沒有新匯報時，顯示「輪到你」的事項（`todo` 且到期，或在等使用者的），一則一行，點了打開負責的 Bot。

**工具**（只給腳本，兩個就夠）：

- `note_item`：新增或更新一筆（給 id 就是更新），包括結案。
- `list_items`：列出事項：輪到使用者的、在等的、過期的；預設只列這個 Bot 的，可以要全部。

不另做看板畫面，也不讓模型自己維護欄位以外的東西。

## 不做的

- **不把求職資料庫搬進 pi**：職缺、事件是那個 Bot 的帳本，搬了就是兩份。
- **不用雲端待辦（Google Tasks、Notion、Linear）**：生活事項最私人，手機上的 pi 是離隱私最近的那一端。
- **不讓每個 Bot 自訂事項格式**：那就是現在看不到全貌的原因。

## 要使用者決定

1. 求職資料庫的 `tasks` 表：改由「事項」接手（Bot 之後只寫事項，`tasks` 不再用），還是兩邊都留？兩邊都留就是同一件事記兩份。
2. 財務管家的「到某個價位才考慮」這類條件，要不要也寫成事項（`waiting`，`waiting_on` 寫條件，每天的彙報排程順便檢查），還是維持現在寫在記憶裡。
3. `facts` 裡那筆 GitHub token 要不要搬到 pi 的憑證存放處，並從資料庫刪掉。

## 分階段

1. **事項與到期叫醒**：`note_item`、`list_items`，`next_at` 接上精確鬧鐘。用真的事驗收：「週五前要回覆某公司面試時間」到期會叫醒並通知；「等某人回信」在 `next_at` 叫醒追問。
2. **輪到你**：桌面小工具在沒有新匯報時列出輪到使用者的事項。
3. **等別人回覆就醒**：`waiting_on` 是人或 app 時掛通知事件。
4. **求職管家接手**：照第 1 個決定，把未完成的待辦和有下一步的職缺轉成事項。

每一階段先用 SOTA 模型把真的事辦成，再用 Qwen3.6 跑同樣的事（[computer-agents.md](computer-agents.md) 的做法）。
