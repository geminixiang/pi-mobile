# 生活事項：Bot 怎麼替使用者記住「還有什麼事」

2026-10-31 起草，2026-11-01 做完四個階段。問題：pi 的 Bot 要用什麼工具，才能把使用者生活上的瑣事管好（期限、繳費、等別人回覆、等某個條件）。開發 pi-mobile 本身的待辦另用 GitHub Issues，不在這裡。

## 起草時看到的問題

看了使用者每天在用的 Bot 怎麼記事情（只看結構，內容不寫進這份公開文件）：有的在電腦上自己建資料庫記待辦，有的把要注意的條件寫在記憶文字裡，手機上的共用資料庫沒人用。

- **期限到了沒人叫**：資料庫有期限欄位，但沒有任何東西在期限時叫醒 Bot 或使用者，只有定時掃描順便看到才會提。
- **「下一步」多半沒有時間**。
- **「等誰」藏在各自的欄位或記憶裡**：使用者沒有地方一次看到「現在輪到我的事」。
- **每個 Bot 各記一套、各放一處**：換一個 Bot 或換一個模型，就要重新理解那套結構。
- **機密混在資料裡**：機密應該放 pi 的憑證存放處，不該在 Bot 的資料表或記憶裡。

## 生活事項有哪幾種

需要 Bot 再回來處理的事只有三種：

1. **某個時間要做**：期限前回覆、繳費、回診。
2. **在等別人**：等對方回覆、等退款。等到了要有人知道。
3. **條件成立才要做**：某個價位以下、到某個地點、收到某人的訊息。

三種都需要「到時候自己冒出來」，這是看板做不到的，也是現在缺的。

## 設計：一份手機上的「事項」，Bot 共用

**原則：領域資料留在原地，只把「需要再回來看的事」收成一份。** Bot 自己的資料庫是它的帳本，繼續留在原地；pi 只多記一份很薄的「事項」，指回帳本裡的那一筆。

**一筆事項的欄位**（少，讓小模型也寫得對）：

| 欄位 | 內容 |
|---|---|
| `title` | 一句話，使用者看得懂 |
| `state` | `todo`（輪到使用者或 Bot 做）／`waiting`（在等別人或某個條件）／`done` |
| `next_at` | 什麼時候再看一次（期限、追蹤日）；沒有就是「不用主動看」 |
| `waiting_on` | 在等誰或什麼（`waiting` 才有）：一個人、一個 app 的訊息、一個條件 |
| `bot` | 負責的 Bot，到時候叫醒它 |
| `ref` | 指回帳本的那一筆（Bot 資料庫裡的一筆、一個網址），可以沒有 |

- 存在 pi 自己的資料（跟排程一樣是 durable 的文件，只在手機上），不放雲端，也不放使用者的 SQLite（那是給使用者自己的表用的）。
- `state` 是互斥的一個值，不用多個布林欄位湊。

**到時候叫醒**：`next_at` 直接接上排程的精確鬧鐘（跟「等它做完」的 `watch` 同一套）。到了就叫醒負責的 Bot，帶著那筆事項；Bot 照無人值守的規則處理，需要使用者時通知。沒有 `next_at` 的事項不會自己冒出來，所以 Bot 寫事項時要給。

**在等別人**：`waiting_on` 是某個人或 app 時，可以再掛現有的通知事件（`on: notification`，`app`、`contains`）：對方一回就叫醒 Bot，不用等到 `next_at`。

**讓使用者一眼看到**：桌面小工具在沒有新匯報時，顯示「待辦」：要使用者處理的事項（`todo` 且到期，或在等使用者的），一則一行，寫「負責的 Bot · 幾點到期」（沒設時間寫「未定時間」，過了寫「已過期」），由系統的列表排版，放不下的可以捲動；點了打開負責的 Bot。

**工具**（只給腳本，兩個就夠）：

- `note_item`：新增或更新一筆（給 id 就是更新），包括結案。
- `list_items`：列出事項：輪到使用者的、在等的、過期的；預設只列這個 Bot 的，可以要全部。

不另做看板畫面，也不讓模型自己維護欄位以外的東西。

## 不做的

- **不把 Bot 自己的資料庫搬進 pi**：那是它的帳本，搬了就是兩份。
- **不用雲端待辦（Google Tasks、Notion、Linear）**：生活事項最私人，手機上的 pi 是離隱私最近的那一端。
- **不讓每個 Bot 自訂事項格式**：那就是現在看不到全貌的原因。

## 使用者的決定（2026-11-01）

1. Bot 自己資料庫裡的待辦表由事項接手：原本的表留作歷史、不刪不改，之後只寫事項。同類、沒有期限的事合成一件分類事項，被合併的以 `done` 結案。
2. 「到某個條件才考慮」寫成 `waiting` 的事項（`waiting_on` 寫條件，不給 `next_at`），記憶裡不再重複；原本定時彙報的排程每次先 `list_items` 檢查，成立就通知並改成 `todo`。

## 分階段

1. **事項與到期叫醒**：`note_item`、`list_items`，`next_at` 接上精確鬧鐘。用真的事驗收：「週五前要回覆某件事」到期會叫醒並通知；「等某人回信」在 `next_at` 叫醒追問。
2. **輪到你**（2026-11-01 做了，模擬器驗證，見 [tools.md](../tools.md) 紀錄）：桌面小工具在沒有新匯報時列出輪到使用者的事項。
3. **等別人回覆就醒**（2026-11-01 做了，模擬器驗證，見 [tools.md](../tools.md) 紀錄）：在等的事項給 `wake_app` 或 `wake_contains` 時掛通知事件，跟 `next_at` 並存；對方一回就叫醒，`next_at` 是沒回時去追的時間。只有出現在這支手機通知裡的回覆收得到（簡訊、LINE、Gmail），寄到電腦的信要靠 `next_at`。
4. **既有的 Bot 接手**（2026-11-01 做了，S24）：照上面的決定，請 Bot 自己把未完成的待辦轉成事項，`ref` 指回原本的資料庫。

每一階段先用 SOTA 模型把真的事辦成，再用 Qwen3.6 跑同樣的事（[computer-agents.md](computer-agents.md) 的做法）。
