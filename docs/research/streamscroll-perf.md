# streamscroll 掉的幀，時間花在哪裡

2026-11-24，S24（SM-S9210，Android 17，WebView 157.0.8103.52，120 Hz），分支 `perf-hunt`。基準是 main 的 `b4c8fe8`，實驗是 `7520ae6`（下一個 commit `4224c0d` 撤回），兩個 APK 都用發布金鑰簽（SHA-256 `fefa5363…cac1`，和手機上原本的 pi 同一把）。

## 結論

**`streamscroll` 的 12 % 大部分不是使用者看得到的卡頓。** 掉的幀約八成五是「畫面閒了一陣子之後的第一幀」：回答在畫面外面串流，每一批字進來，pi 就重畫一次整個畫面，而 GPU 在兩批之間已經降到最低頻（231 MHz），第一幀要 8–10 ms 才畫完。這些幀裡畫面上沒有東西在動。真的在捲動中掉的幀，每次只有 3–25 幀（連續幀的 1–2 %），和只捲不串流的 `scroll`（0.6 %）同一個量級。

- 卡的是 GPU，不是 JavaScript、樣式或排版：慢的幀 GPU 等了 8–10 ms，正常的幀 0.5–0.7 ms；主執行緒每幀約 6 ms，在預算內。
- 為什麼一直重畫：串流中的那則回答變長，對話的捲動高度跟著變，整個看得到的區域都要重新合成（見「原因」）。
- 試了一個修法（讓畫面外的串流回答不排版）：注入 CSS 時掉幀減半，做成 build 之後**沒有差別**（11.9 % 對 12.5 %），原因還沒找到。所以**現在不建議改 app**。
- 建議先改量法：`run.ts` 把「閒置後的第一幀」和「連續動畫中的慢幀」分開算（見最後一節）。

## 怎麼量的

1. **重現。** 自己 build 的 main 裝上去，fixture 30 則回答，`run.ts --scenes streamscroll --runs 5`：12.6 %（12.1–12.9），超過 12 ms 107 幀，慢在送出繪製指令的 155 幀，rAF 超時 1.5 %、LoAF 0。和已知的 12 % 一樣。
2. **抓 trace。** 一次 `streamscroll` 開著 Perfetto 系統 trace（sched、cpufreq、gfx/view/webview/input 的 atrace、SurfaceFlinger 的 frametimeline、WebView 的 `track_event`），結束時存 `dumpsys gfxinfo framestats`。手機上 205 MB，壓縮後 42 MB 拉回 Mac，用 trace_processor 分析。另外用 CDP 的 `LayerTree` 看每一層重畫幾次、對到哪個 DOM 節點，用 `MutationObserver` 看串流時畫面裡有沒有東西變。
3. **把每一幀拆開。** 用 RenderThread 的 `DrawFrames <id>`、主執行緒的 `Choreographer#doFrame <id>`、`GPU completion` 執行緒的 `waitForever` 拼出每一幀從 vsync 到 GPU 畫完的時間。和 gfxinfo framestats 重疊的 120 幀逐幀比對，差距中位數 −0.9 ms（p10 −1.2、p90 −0.6），所以 trace 裡每一幀的分類可以信。
4. **注入 CSS 的比較**（同一個 session 交替，不重裝），再用 **build 的 A/B** 證明。

trace 和抓的時候：充電中（使用者允許步驟 1–4 充電），熱狀態 0、AP 38–48 °C；每次都記在 `/tmp/perf-hunt/*-heat.json` 或 `ab*.jsonl`。腳本和原始資料都在 `/tmp/perf-hunt/`（不進 git）：`capture.ts`（trace）、`frames.py`、`breakdown.py`、`raster.py`、`layers.py`（trace 分析）、`layers.ts`（LayerTree）、`probe.ts`（MutationObserver）、`ab.ts`（注入比較，每 0.7 秒讀一次 framestats，所以每一幀都有）、`round.sh`（A/B 的一輪）、`where.ts`（串流回答在畫面的哪裡）。

## 掉的幀在哪裡

### 場景本身：捲完不會回到底部

`streamscroll` 在送出後 1.5 秒開始，往上滑兩次、往下滑兩次，一共約 6 秒。滑完時離底部還有 934 px（`capture.ts` 每滑一次記一次：2654、5002、2977、934），串流還要再跑約 35 秒。這 35 秒畫面停著，回答在可見範圍下面一直長。所以 42 秒裡，捲動只佔 6 秒，剩下都是「停著、回答在畫面外長」。

### 每一幀的分類（trace，充電中，有 trace 的負擔）

| 時段 | 幀數 | 超過 11.5 ms | 慢的幀裡最大的一段 |
|---|---|---|---|
| 送出到第一次滑之前 | 131 | 4 | RenderThread 3、主執行緒 1 |
| 滑動中（手指加慣性 1.3 秒） | 661 | 194 | GPU 165、主執行緒 13、RenderThread 10、等 buffer 6 |
| 兩次滑動之間 | 22 | 11 | GPU 8 |
| 滑完、停著 | 477 | 109 | GPU 102、RenderThread 7 |

慢的幀各段的中位數：從 vsync 到畫完 14–16 ms，其中主執行緒 1.2–1.6 ms、RenderThread 3.9–6.6 ms、**GPU 8.2–8.5 ms**；正常的幀 GPU 0.5–0.7 ms。主執行緒（App 的 UI 執行緒）和 WebView 的 Viz 都很短；SurfaceFlinger 的 frametimeline 把這些幀大多標成 `Buffer Stuffing`（準時上螢幕）或 `Non Animating`，真的「App Deadline Missed」整段只有 6 幀。

**停著的時段，慢的幀就是閒置後的第一幀。** 按離上一幀多久分：

| 停著的時段 | 幀數 | 慢的 | GPU 中位數 |
|---|---|---|---|
| 離上一幀 ≤ 9 ms | 167 | 2（1 %） | 0.5 ms |
| 9–60 ms | 96 | 5 | 0.5 ms |
| > 60 ms | 214 | 102（48 %） | 6.5 ms |

framestats 也看得到同一個樣子：停著時每 150–200 ms（就是 fixture 每一批的間隔）來 1–3 幀，第一幀 13–17 ms，幾乎全是等 GPU（swap 之後 8–12 ms），後面的 5–7 ms。`docs/research/render.md` 量到的「更新越稀疏越容易掉幀」是同一件事。

**不開 trace 時，閒置後的幀佔得更多。** `ab.ts` 拿到每一幀之後（不開 trace，10 次 base），超過 11.5 ms 的幀每次 58–138 幀，其中閒置 60 ms 以上之後的 44–120 幀，連續動畫中（離上一幀 ≤ 20 ms）的只有 4–25 幀，佔連續幀（約 830–1,000 幀）的 0.4–2.5 %。trace 自己的負擔把滑動中的慢幀放大了。

**CPU。** 手指一碰，中核和大核的最低頻率被拉到 2.3 GHz（`Cpu 2/5/7 Min Freq Limit`，觸控加速），所以滑動中的慢幀不是 CPU 降頻。GPU 頻率 trace 沒抓到（`power/gpu_frequency` 這台沒有）；`/sys/class/kgsl/kgsl-3d0/devfreq/cur_freq` 閒著時是 231 MHz，可用的有 80 MHz 到 1 GHz。

## 原因

### 停著時為什麼一直重畫

`MutationObserver` 在停著的 10 秒裡記下 1,666 次改動，在可見範圍裡的只有 `.transcript` 和輸入框 `.input` 各 2 次（加一個子節點）；同一段時間 App 畫了 467 幀。畫面上沒有東西變，卻一直畫，來源是：

- **串流的回答一變長，捲動高度就變。** 合成器把對話的捲動內容當成一層（`div.transcript`，6 萬多 px 高），在它後面還有一層「最後一張表格之後的所有內容」（見下一節）；兩層的大小每一批都變，合成器把整個看得到的範圍當成要重畫。LayerTree 看到串流的那一層在停著時重畫了 437–465 次。
- **捲軸**也跟著變長變短：`scrollbar-width: none` 時，同樣 10 秒從 467 幀降到 164 幀，但掉的幀反而 36 → 57（更稀疏，每一幀都是閒置後的第一幀）。
- **標題列膠囊的游標**（`.bar-cursor`，忙的時候在 Bot 名字後面閃）用 `steps(1)` 一秒變兩次，每次都是真的改變，也是一幀閒置後的第一幀。關掉它（注入 `.bar-cursor { animation: none; }`）每次少約 40 個掉幀（155、159 → 112、118）。

證明串流就是主因的對照：把串流中的文字藏起來（注入 `.markdown.caret { display: none; }`，只是診斷），畫的幀從約 1,280 降到 770–851，掉幀 125–176 → 77–87（4 次）。

### 滑動中：表格把對話切成好幾層

`.markdown .table { overflow-x: auto; }` 的表格在手機上真的比畫面寬（1,176 px 對 1,080 px），所以每一張都是可以左右捲的捲動區塊，合成器給它自己一層。表格之後畫的所有內容不能再併回對話那一層，就另開一層（LayerTree 用第一個節點命名，都是 `blockquote`），10,000–16,800 px 高。舊的訊息有 `content-visibility: auto`，滑動時一則進出畫面，裡面的表格出現或消失，這些大層就整層重建、換一個新的 id（同一次 6 秒的滑動裡 175 → 190 → 197 → 202 → 207），新的層要從頭點陣化。Perfetto 裡 GPU 執行緒的點陣化工作在滑動中大多是這些新 id 的層；滑動中慢的幀有 80 % 前面剛好有點陣化，正常的幀是 43 %，停著時慢的幀只有 3 %。

**只捲不串流時也一樣重建**（`layers.ts scroll`：一樣有 232、235、244 這些新的 `blockquote` 層），而 `scroll` 只掉 0.6 %，所以它不是主因。注入 `.markdown .table { overflow-x: hidden; }`（只是診斷，會讓表格不能左右捲）也在誤差內（179、176 對 177、150）。

### 「有新內容」的脈衝讓輸入框每一幀重畫

捲離底部、又有新內容時，「最新」按鈕變成 `.scroll-hint.new`，跑兩次 1.6 秒的 `hint-pulse`（`box-shadow` 動畫）。LayerTree 看到這段時間整個輸入框（`div.composer`，1080 × 351）重畫了 309–344 次，只捲不串流時 2 次，拿掉動畫後 0 次。它違反 `.pi/skills/css/SKILL.md` § 4（常常跑的動畫只用 `opacity`、`transform`），但量不出 gfx 的差別（注入關掉：174、147 對 177、150）。

## 建議

1. **先改量法，不改 app。**`run.ts` 已經有 gfxinfo；加上像 `ab.ts` 那樣每 0.7 秒讀一次 framestats，把慢的幀分成「連續動畫中」（離上一幀 ≤ 20 ms）和「閒置後的第一幀」兩個數字，`streamscroll` 看前者。代價：`run.ts` 約多 30 行，量測時多一個每 0.7 秒的 `dumpsys`（這次沒看出影響，但沒有單獨量），以後的數字和以前的 12 % 不能直接比。另一個做法是讓場景滑回底部，但那就不再量「串流時停在上面看」這件常見的事。
2. **app 這邊沒有值得做的。**使用者看得到的（滑動中的慢幀）和 `scroll` 同一個量級；閒置後的幀畫面沒有動，晚一幀看不出來，只多耗電。讓畫面外的串流回答不排版（`content-visibility`）在 build 量不出差別，不做。
3. **之後可以再看的線索**（都量不出 gfx 差別，或還沒解開）：
   - 選擇器寫法造成的差別（上一節），解開後也許有一個真正少畫 470 幀的做法。
   - 標題列游標的 `steps(1)` 閃爍每秒叫醒 GPU 兩次（約 40 個掉幀），但這是看得到的回饋，改它是設計的事。
   - 「有新內容」的 `box-shadow` 脈衝讓輸入框每幀重畫（違反 CSS 規則 § 4，但量不出 gfx 差別）；表格的捲動區塊把對話切成會一直重建的大層。

## 量測時踩到的

- 無線偵錯在拉 42 MB 的 trace 時斷過一次，序號從 `:33655` 換成 `:33477`。之後同一條線 2.7 MB/s（之前 0.1 MB/s，裝一次 APK 要 6 分鐘）。
- 接上充電器那一刻 pi 被切到桌面，接著一次探測的兩下滑動送到了桌面，pi 回到前景時開的是另一個 Bot。那次沒有東西送到那個 Bot（查過那個對話）；之後每支腳本送出前都確認開著的是「測試效能」、滑動前確認 pi 在前面，再用 `fixture.ts setup` 換回測試 Bot（docs/development.md 的做法）。
- trace 會放大滑動中的慢幀（有 trace 時 194 幀，沒有時每次 4–25 幀），比較數字要用沒開 trace 的量法。
