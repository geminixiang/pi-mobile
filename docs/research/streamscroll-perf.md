# streamscroll 掉的幀，時間花在哪裡

2026-11-24，S24（SM-S9210，Android 17，WebView 157.0.8103.52，120 Hz），分支 `perf-hunt`。基準是 main 的 `b4c8fe8`，所有 APK 都用發布金鑰簽（SHA-256 `fefa5363…cac1`，和手機上原本的 pi 同一把）。上午是第一輪（找原因），下午是第二輪（修，見最後一節「第二輪」）。

## 結論

**修完之後，四個場景都在 5 % 以下。** `streamscroll` 12–13 % → 2.1 %（設計 B 的 build，5 次），靠的是兩件事：使用者往上看的時候，串流的字最多每秒寫一次；標題列的忙碌記號不再閃（改成頭像右下角不動的黃點）。`stream`、`scroll`、`panel` 沒有變差。

第一輪的結論（仍然成立）：**`streamscroll` 的 12 % 大部分不是使用者看得到的卡頓。** 掉的幀約八成五是「畫面閒了一陣子之後的第一幀」：回答在畫面外面串流，每一批字進來，pi 就重畫一次整個畫面，而 GPU 在兩批之間已經降到最低頻（231 MHz），第一幀要 8–10 ms 才畫完。這些幀裡畫面上沒有東西在動。真的在捲動中掉的幀，每次只有 3–25 幀（連續幀的 1–2 %），和只捲不串流的 `scroll`（0.6 %）同一個量級。

- 卡的是 GPU，不是 JavaScript、樣式或排版：慢的幀 GPU 等了 8–10 ms，正常的幀 0.5–0.7 ms；主執行緒每幀約 6 ms，在預算內。
- 為什麼一直重畫：串流中的那則回答變長，對話的捲動高度跟著變，整個看得到的區域都要重新合成（見「原因」）。
- 第一輪試的修法（讓串流的回答在畫面外時不排版）注入 CSS 時掉幀減半、build 之後沒有差別：注入的那個是量測腳本的錯（第二輪「選擇器的謎」），它本來就只在整則回答都在畫面外時有用。

## 怎麼量的

1. **重現。** 自己 build 的 main 裝上去，fixture 30 則回答，`run.ts --scenes streamscroll --runs 5`：12.6 %（12.1–12.9），超過 12 ms 107 幀，慢在送出繪製指令的 155 幀，rAF 超時 1.5 %、LoAF 0。和已知的 12 % 一樣。
2. **抓 trace。** 一次 `streamscroll` 開著 Perfetto 系統 trace（sched、cpufreq、gfx/view/webview/input 的 atrace、SurfaceFlinger 的 frametimeline、WebView 的 `track_event`），結束時存 `dumpsys gfxinfo framestats`。手機上 205 MB，壓縮後 42 MB 拉回 Mac，用 trace_processor 分析。另外用 CDP 的 `LayerTree` 看每一層重畫幾次、對到哪個 DOM 節點，用 `MutationObserver` 看串流時畫面裡有沒有東西變。
3. **把每一幀拆開。** 用 RenderThread 的 `DrawFrames <id>`、主執行緒的 `Choreographer#doFrame <id>`、`GPU completion` 執行緒的 `waitForever` 拼出每一幀從 vsync 到 GPU 畫完的時間。和 gfxinfo framestats 重疊的 120 幀逐幀比對，差距中位數 −0.9 ms（p10 −1.2、p90 −0.6），所以 trace 裡每一幀的分類可以信。
4. **注入 CSS 的比較**（同一個 session 交替，不重裝），再用 **build 的 A/B** 證明。

trace 和抓的時候：充電中（使用者允許步驟 1–4 充電），熱狀態 0、AP 38–48 °C；每次都記在 `/tmp/perf-hunt/*-heat.json` 或 `ab*.jsonl`。腳本和原始資料都在 `/tmp/perf-hunt/`（不進 git）：`capture.ts`（trace）、`frames.py`、`breakdown.py`、`raster.py`、`layers.py`（trace 分析）、`layers.ts`（LayerTree）、`probe.ts`（MutationObserver）、`ab.ts`（注入比較，每 0.7 秒讀一次 framestats，所以每一幀都有）、`round.sh`（A/B 的一輪）、`where.ts`（串流回答在畫面的哪裡）。

## 掉的幀在哪裡

### 場景本身：捲完不會回到底部

`streamscroll` 在送出後 1.5 秒開始，往上滑兩次、往下滑兩次，一共約 6 秒。滑完時離底部還有 934 px（`capture.ts` 每滑一次記一次：2654、5002、2977、934），串流還要再跑約 35 秒。這 35 秒畫面停著，回答在可見範圍下面一直長。所以 42 秒裡，捲動只佔 6 秒，剩下都是「停著、回答在畫面外長」。

### 每一幀的分類（trace，充電中，有 trace 的負擔）

| 時段 | 幀數 | 超過 11.5 ms | 慢的幀裡最大的一段 |
|---|---|---|---|
| 送出到第一次滑之前 | 131 | 4 | RenderThread 3、主執行緒 1 |
| 滑動中（手指加慣性 1.3 秒） | 661 | 194 | GPU 165、主執行緒 13、RenderThread 10、等 buffer 6 |
| 兩次滑動之間 | 22 | 11 | GPU 8 |
| 滑完、停著 | 477 | 109 | GPU 102、RenderThread 7 |

慢的幀各段的中位數：從 vsync 到畫完 14–16 ms，其中主執行緒 1.2–1.6 ms、RenderThread 3.9–6.6 ms、**GPU 8.2–8.5 ms**；正常的幀 GPU 0.5–0.7 ms。主執行緒（App 的 UI 執行緒）和 WebView 的 Viz 都很短；SurfaceFlinger 的 frametimeline 把這些幀大多標成 `Buffer Stuffing`（準時上螢幕）或 `Non Animating`，真的「App Deadline Missed」整段只有 6 幀。

**停著的時段，慢的幀就是閒置後的第一幀。** 按離上一幀多久分：

| 停著的時段 | 幀數 | 慢的 | GPU 中位數 |
|---|---|---|---|
| 離上一幀 ≤ 9 ms | 167 | 2（1 %） | 0.5 ms |
| 9–60 ms | 96 | 5 | 0.5 ms |
| > 60 ms | 214 | 102（48 %） | 6.5 ms |

framestats 也看得到同一個樣子：停著時每 150–200 ms（就是 fixture 每一批的間隔）來 1–3 幀，第一幀 13–17 ms，幾乎全是等 GPU（swap 之後 8–12 ms），後面的 5–7 ms。`docs/research/render.md` 量到的「更新越稀疏越容易掉幀」是同一件事。

**不開 trace 時，閒置後的幀佔得更多。** `ab.ts` 拿到每一幀之後（不開 trace，10 次 base），超過 11.5 ms 的幀每次 58–138 幀，其中閒置 60 ms 以上之後的 44–120 幀，連續動畫中（離上一幀 ≤ 20 ms）的只有 4–25 幀，佔連續幀（約 830–1,000 幀）的 0.4–2.5 %。trace 自己的負擔把滑動中的慢幀放大了。

**CPU。** 手指一碰，中核和大核的最低頻率被拉到 2.3 GHz（`Cpu 2/5/7 Min Freq Limit`，觸控加速），所以滑動中的慢幀不是 CPU 降頻。GPU 頻率 trace 沒抓到（`power/gpu_frequency` 這台沒有）；`/sys/class/kgsl/kgsl-3d0/devfreq/cur_freq` 閒著時是 231 MHz，可用的有 80 MHz 到 1 GHz。

## 原因

### 停著時為什麼一直重畫

`MutationObserver` 在停著的 10 秒裡記下 1,666 次改動，在可見範圍裡的只有 `.transcript` 和輸入框 `.input` 各 2 次（加一個子節點）；同一段時間 App 畫了 467 幀。畫面上沒有東西變，卻一直畫，來源是：

- **串流的回答一變長，捲動高度就變。** 合成器把對話的捲動內容當成一層（`div.transcript`，6 萬多 px 高），在它後面還有一層「最後一張表格之後的所有內容」（見下一節）；兩層的大小每一批都變，合成器把整個看得到的範圍當成要重畫。LayerTree 看到串流的那一層在停著時重畫了 437–465 次。
- **捲軸**也跟著變長變短：`scrollbar-width: none` 時，同樣 10 秒從 467 幀降到 164 幀，但掉的幀反而 36 → 57（更稀疏，每一幀都是閒置後的第一幀）。
- **標題列膠囊的游標**（`.bar-cursor`，忙的時候在 Bot 名字後面閃）用 `steps(1)` 一秒變兩次，每次都是真的改變，也是一幀閒置後的第一幀。關掉它（注入 `.bar-cursor { animation: none; }`）每次少約 40 個掉幀（155、159 → 112、118）。

證明串流就是主因的對照：把串流中的文字藏起來（注入 `.markdown.caret { display: none; }`，只是診斷），畫的幀從約 1,280 降到 770–851，掉幀 125–176 → 77–87（4 次）。

### 滑動中：表格把對話切成好幾層

`.markdown .table { overflow-x: auto; }` 的表格在手機上真的比畫面寬（1,176 px 對 1,080 px），所以每一張都是可以左右捲的捲動區塊，合成器給它自己一層。表格之後畫的所有內容不能再併回對話那一層，就另開一層（LayerTree 用第一個節點命名，都是 `blockquote`），10,000–16,800 px 高。舊的訊息有 `content-visibility: auto`，滑動時一則進出畫面，裡面的表格出現或消失，這些大層就整層重建、換一個新的 id（同一次 6 秒的滑動裡 175 → 190 → 197 → 202 → 207），新的層要從頭點陣化。Perfetto 裡 GPU 執行緒的點陣化工作在滑動中大多是這些新 id 的層；滑動中慢的幀有 80 % 前面剛好有點陣化，正常的幀是 43 %，停著時慢的幀只有 3 %。

**只捲不串流時也一樣重建**（`layers.ts scroll`：一樣有 232、235、244 這些新的 `blockquote` 層），而 `scroll` 只掉 0.6 %，所以它不是主因。注入 `.markdown .table { overflow-x: hidden; }`（只是診斷，會讓表格不能左右捲）也在誤差內（179、176 對 177、150）。

### 「有新內容」的脈衝讓輸入框每一幀重畫

捲離底部、又有新內容時，「最新」按鈕變成 `.scroll-hint.new`，跑兩次 1.6 秒的 `hint-pulse`（`box-shadow` 動畫）。LayerTree 看到這段時間整個輸入框（`div.composer`，1080 × 351）重畫了 309–344 次，只捲不串流時 2 次，拿掉動畫後 0 次。它違反 `.pi/skills/css/SKILL.md` § 4（常常跑的動畫只用 `opacity`、`transform`），但量不出 gfx 的差別（注入關掉：174、147 對 177、150）。

## 第一輪的建議（第二輪做了）

1. 量法分開兩種慢幀：做了（`run.ts` 的 `gfxSlowMoving`、`gfxSlowAfterIdle`）。
2. 不改 app：第二輪使用者同意了兩個改動（字在看不到時少寫、忙碌記號不閃），量得出來，見下一節。
3. 線索：選擇器的謎解開了；標題列游標換成不動的黃點；「有新內容」的脈衝和表格的大層還在，量不出 gfx 差別。

## 量測時踩到的

- 無線偵錯在拉 42 MB 的 trace 時斷過一次，序號從 `:33655` 換成 `:33477`。之後同一條線 2.7 MB/s（之前 0.1 MB/s，裝一次 APK 要 6 分鐘）。
- 接上充電器那一刻 pi 被切到桌面，接著一次探測的兩下滑動送到了桌面，pi 回到前景時開的是另一個 Bot。那次沒有東西送到那個 Bot（查過那個對話）；之後每支腳本送出前都確認開著的是「測試效能」、滑動前確認 pi 在前面，再用 `fixture.ts setup` 換回測試 Bot（docs/development.md 的做法）。
- trace 會放大滑動中的慢幀（有 trace 時 194 幀，沒有時每次 4–25 幀），比較數字要用沒開 trace 的量法。

## 第二輪：修到 5 % 以下

目標：`scroll`、`stream`、`streamscroll`、`panel` 的 gfx 掉幀（全部的幀）都在 5 % 以下。每一個改動都和 base 交替量：每一輪重裝那一版、重開 pi、fixture 先拆再建、暖機 1 次量 5 次，沒充電，熱狀態每次 0。原始結果在 `test/perf/out/s2-*.json`、`s4-*.json`（不進 git），彙整用 `/tmp/perf-hunt/summ.js`。

### 1. 量法：`run.ts` 分出兩種慢幀

`run.ts` 每 0.7 秒讀一次 `gfxinfo framestats`，在 `gfxJankyPct` 旁邊多報 `gfxSlowMoving`（連續動畫中、超過 1.5 個 vsync 的幀）、`gfxSlowMovingPct` 和 `gfxSlowAfterIdle`（閒了 4 個 vsync 以上之後的第一幀）。目標仍然是 `gfxJankyPct`。framestats 抓到的幀數和 gfxinfo 的總數差不到 3 %（base：1,277–1,343 對 1,289–1,358）。

| `streamscroll`（base，2 輪 × 5 次） | 中位數（範圍） |
|---|---|
| gfx 掉幀 % | 13.1（11.0–13.4），兩輪 13.1、11.8 |
| 連續動畫中的慢幀 | 11（9–13），約 1 % |
| 閒置後第一幀的慢幀 | 100（74–108） |

「慢」是從 vsync 到畫完超過 12.5 ms，和 gfxinfo 的 deadline 不同（gfxinfo 容許排隊中的 buffer），所以 `panel` 這種一直在動的場景，`gfxSlowMoving`（17–109）會比 gfxinfo 算的掉幀（10–16）多，那個場景要看總數。

### 2. 選擇器的謎：是量測腳本的錯

第一輪注入 `.transcript > article.answer:last-of-type { content-visibility: auto }` 時少畫約 470 幀，寫成 `.answer.streaming` 卻沒有。原因在 `ab.ts`，不在畫面（問了一次 Claude Fable 5.2，`/tmp/perf-hunt/fable-selector.md`，再在 S24 上驗證）：

- `ab.ts` 在同一個 task 裡注入 CSS、接著 `scrollTop = 1e9`。`:last-of-type` 在那一刻選中的是**上一則已經寫完的回答**（約 15,000 px），它先被略過、高度塌掉，捲到的「底部」其實離真的底部約 5,000 px；下一幀它展開，畫面就停在上面，app 也沒有重新黏到底。
- 於是新的串流回答一出生就在畫面外 5,000 px 以下，整次都沒有畫，和「把串流文字藏起來」的診斷一樣（連續幀 688–738 對 678–707，base 912–1,006）。
- 驗證：`ab.ts` 改成注入後等兩個動畫幀、捲到底、確認離底不到 4 px 才送出，同樣的 `:last-of-type` 就是 1,304、1,324 幀，和 base（1,323、1,332）一樣。
- 桌機 Chrome 那次也沒有測到 `.answer.streaming`：web build 裡根本沒有 `streaming` 這個 class。

所以 `.answer.streaming` 的規則是對的，只是它只在**整則**回答都在畫面外時有用；`streamscroll` 滑完時回答的頂端還在畫面上，用不到。把畫面停在上面 4,000 px（`/tmp/perf-hunt/farpark.ts`：串流中往上滑兩次，量 10 秒）：

| 停在上面 4,000 px 的 10 秒 | 畫的幀 | 掉幀 | 串流回答 |
|---|---|---|---|
| base（2 次） | 170、170 | 47、43 | 一直排版，捲動高度一直長 |
| `.streaming` 加 `content-visibility: auto`（2 次） | 67、82 | 20、20 | 內容被略過，捲動高度 10 秒不變 |

剩下的約 20 個掉幀是每秒兩次的游標閃爍（這一版還沒拿掉）。這是 commit「skip the streaming answer while it is far offscreen」。

### 3. 往上看時，串流的字最多每秒寫一次

對話的結尾在畫面下方超過一個畫面時，`useSmoothText` 不再每幀寫字，最多每秒寫一次；回到離結尾一個畫面以內，或回到底部，就照原本的方式追上。`Chat` 擁有一個 `cell`（在原本的 `onScroll` 裡設），經 `Content` 的 `streaming` 傳給 `StreamingMarkdown`；沒有 effect、沒有新的計時器，對話的資料仍然只有一個擁有者。「有新內容」照舊出現，捲軸在往上看時不再一直變長。

| `streamscroll` × 5 | gfx 掉幀 % | 掉幀數 | 畫的幀 | 連續中慢 | 閒置後慢 |
|---|---|---|---|---|---|
| base（2 輪） | 13.1（11.0–13.4） | 173（146–178） | 1,322 | 11 | 100 |
| 往上看時少寫字（1 輪） | 10.8（9.4–11.8） | 107（94–116） | 996 | 18 | 81 |

`test/device/scroll-stick.js` 多了 (g)「串流中往上捲過一個畫面」：3 秒內字寫進去幾次。base 30 次（失敗），最後的 build 3 次（通過），回到底部後兩者都跟著底部。同一支腳本的 (a)「串流中往上捲 20、40 px」在 base 就失敗（小幅往上捲會被拉回底部），不是這次的改動造成的，沒有處理。

### 4. 忙碌記號不閃

字少寫之後，剩下的閒置後慢幀大多是標題列的游標：`steps(1)` 一秒變兩次，每次都叫醒 GPU。先把它在生成時改成不閃（`.bar-cursor.still`），再照使用者選的設計 B 換成頭像右下角不動的黃點（9 px、`--yellow`、外圈 2 px 是膠囊底色），思考、用工具、寫回答時都顯示，從來不動。側欄的 PiMark 和 Bot 列表的閃爍記號沒有改；之後也可以用同一個黃點標出忙碌中的 Bot。

| `streamscroll` × 5 | gfx 掉幀 % | 掉幀數 | 畫的幀 | 閒置後慢 | rAF 超時 % |
|---|---|---|---|---|---|
| 少寫字 + 游標不閃（2 輪） | 2.5（2.0–3.1），兩輪 2.5、2.5 | 21（17–27） | 863 | 35（23–39） | 32.5 |
| 最後的 build（步驟 2+3+不閃游標，1 輪） | 2.6（2.3–3.2） | 22 | 866 | 32 | 32.8 |
| 最後的 build，同一段時間再量（2 輪） | 2.2（1.6–2.8），兩輪 2.2、2.1 | 19（14–24） | 867 | 34（19–42） | 32.6 |
| 設計 B：頭像黃點（1 輪，和上一列交替） | 2.1（1.6–2.7） | 18（14–24） | 853 | 32（31–39） | 32.8 |

設計 B 只量了一輪：使用者要收尾，第二輪在重裝時停掉。它和不閃的游標一樣不動，量出來也一樣。

**rAF 超時從約 2 % 變成約 33 %，不是卡頓。**沒有閃爍的游標、字又停著時，頁面上沒有東西要畫，WebView 就不再每個 vsync 給頁面一個動畫幀（rAF 從約 4,950 次降到約 2,250 次，`freezes` 是兩幀間隔超過 4 個 vsync）。證據：最後的 build 有一次滑完回到了底部、字一直在動，那一次 rAF 超時 2.6 %、4,873 次；`stream`（一直在動）兩版都是 1.0–1.3 %。

### 5. 其他場景沒有變差

| 場景 × 5 | base | 最後的 build |
|---|---|---|
| `stream` | 2.8 %（2.5–3.2） | 3.3 %（2.7–3.8）；再量 2.6 %，設計 B 2.7 % |
| `scroll` | 1.3 %（0.9–1.5） | 1.3 %（1.0–1.8） |
| `panel` | 4.3 %（2.9–4.7） | 3.5 %（3.4–4.5） |

`stream` 多 0.5 個百分點，比同一版兩輪的浮動（0.7）小，而且那一輪比較熱（AP 44.8–47.8 °C，中途等過一次 61 °C 降溫，base 那輪 42.3–45.3 °C）；設計 B 那段時間再量：最後的 build 2.6 %（兩輪 2.6、2.6，2.5–2.9），設計 B 2.7 %（2.5–3.4），和 base 的 2.8 % 一樣，所以沒有變差。`panel` 量到一半手機被拿去用（Slack 跑到前面，`run.ts` 停在送手勢之前），之後重新量了 5 次。

### 還剩什麼

- 四個場景都在 5 % 以下：`streamscroll` 2.1 %、`stream` 2.7 %、`scroll` 1.3 %、`panel` 3.5 %（`scroll`、`panel` 是不閃游標那一版量的；設計 B 只換了標題列的忙碌記號，這兩個場景 Bot 沒在忙，沒有重量）；最接近的是 `panel`，`streamscroll` 剩下的約 20 個掉幀一半是閒置後的第一幀（每秒一次的寫字、滑動結束），一半是滑動中的慢幀，和 `scroll` 同一個量級。
- 「有新內容」的 `box-shadow` 脈衝每幀重畫輸入框、表格的捲動區塊把對話切成會重建的大層：都還在，量不出 gfx 差別，沒有動。
- `scroll-stick.js` 的 (a) 在 main 上就失敗，值得另外看。
