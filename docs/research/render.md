# 對話畫面的渲染：掉幀從哪裡來

2026-11-06、11-07，S24（SM-S9210，120 Hz），0.16.2 的程式，沒接電。除了標「一輪」的，都是同一天前後各量基準、`test/perf/run.ts` 每組 3 次取中位數。實驗都用臨時 build 或注入 CSS，沒有進 repo。

## 結論

`stream` 的掉幀比例約 1.6%，幾乎都不是 JS。

- 五個場景的掉幀幾乎都是 `Slow issue draw commands`（`stream` 74 幀裡 67 幀），Long Animation Frame 都是 0。
- 貴的是**把正在打的那段有格式內容畫出來**：同樣的 Markdown 和 React 工作放進 `<div hidden>`，只畫純文字，掉幀是 0.2%。
- 換框架、換解析器幫不上忙，少更新反而更糟。
- 讓有格式的內容少變動可以壓低比例，但同一行的版本效果有限，也會讓串流中捲動變差，所以沒做（見「尾巴分段」）。

地板：同一個 WebView 只跑一個小動畫，CSS 動畫 0–0.1%，每幀 JS 更新 0.23%（各 3 次、25 秒）。0.2% 差不多就是地板。

`gfxJankyPct` 的門檻很嚴，只晚一點點也算；使用者看得出來的是連續掉幀和長卡頓，比較時要一起看 `gfxOver33ms`。短場景（`panel` 約 275 幀）一幀就是 0.36%，比例會失真。

## 實驗

### 文字更新頻率（`useSmoothText`）

它每幀更新文字，看起來是浪費，實際上不能拿掉。各兩輪：

| 更新頻率 | 送出幀數 | 掉幀 | 超過 12 ms | 超過 33 ms |
|---|---|---|---|---|
| 120 Hz（現在） | 約 4,680 | 1.6% | 19–28 | 0–2 |
| 60 Hz | 約 3,250 | 25–26% | 47–59 | 0–2 |
| 30 Hz | 約 1,740 | 43–45% | 120–135 | 0 |
| 每 150 ms | 約 550 | 61–67% | 185–214 | 13–14 |

GPU 在每種頻率都停在最低的 231 MHz，使用率從 19% 掉到 1.5%；CPU 中核從約 2,300 MHz 掉到約 1,550 MHz（每 100 ms 取樣，各 1–2 輪）。掉幀和 CPU 降頻同時發生，但沒有證明是原因。

### 最後一段

| 最後一段 | 掉幀 | 繪製慢的幀 |
|---|---|---|
| 全部 Markdown（現在） | 1.5–1.6% | 63–74 |
| 程式碼、表格不解析（一輪） | 0.8% | 32–36 |
| 一般段落不解析（一輪） | 1.2% | 47–58 |
| 全部純文字 | 0.2% | 7–14 |
| Markdown 照做但藏起來，只畫純文字（一輪） | 0.2% | 8–15 |

串流中 DOM 不是重建：一輪只新增 369 個節點，4,262 次是改文字。開著 trace 比較（只看比例），有格式的最後一段 `InlineNode::ShapeText` 2.7 秒、純文字 0.36 秒，`Layout` 5.0 秒、2.2 秒，`PaintArtifactCompositor::Update` 1,671 次、430 次。

### 尾巴分段

最後一段每 N 字才併進 Markdown，還沒併的先用純文字：

| N | 掉幀 | 繪製慢的幀 | 超過 33 ms |
|---|---|---|---|
| 不分段 | 1.6%、1.9% | 60–84 | 1、1 |
| 120（一輪） | 0.7% | 14–37 | 0 |
| 40 | 0.3%、0.2% | 7–13 | 0、0 |

這是把尾巴另起一段的實驗版，粗體符號也會短暫露出。做成同一行之後的結果：

| 版本 | `stream` 掉幀 | 備註 |
|---|---|---|
| 同一行，遇到符號暫停到下一次合併（5 次） | 4.2% | 暫停讓更新變稀疏，幀數從約 4,900 掉到 3,400 |
| 同一行，不暫停，顯示原始符號 | 0.4% | |
| 同一行，不暫停，濾掉符號（5 次） | 0.9% | 超過 12 ms 的幀 20 → 35 |
| 獨立 `inline-block`，不暫停 | 0.2% | 40 字整塊換行，畫面會跳 |

文字要每幀前進，暫停比什麼都貴。

**決定不做（2026-11-07）。** 最後一版 `stream` 1.6% → 0.9%，但 `streamscroll` 12.7% → 15.3%（繪製慢的幀 155 → 約 190），略長的幀變多，超過 33 ms 的幀本來就是 0。使用者看得出來的卡頓沒有變少，不值得多一段程式。

### 沒有效果的

| 改動 | 掉幀 |
|---|---|
| 隱藏頂欄膠囊 | 1.5%（基準 1.5–1.6%） |
| 拿掉背景格線 | 1.5% |
| 程式碼、表格 `overflow: hidden` | 1.4%、1.5%（第一次的 1.2% 是雜訊） |
| `contain: layout paint style`（一輪） | 1.5%（當時基準 1.8%） |
| `text-rendering: optimizeSpeed`（一輪） | 1.6%（當時基準 1.8%） |

### 其他內容

放在最後幾則回答，用 IntersectionObserver 確認真的進了畫面。`scroll` 基準 0.6%：

| 內容 | 掉幀 | 備註 |
|---|---|---|
| 5 個 sandbox iframe（靜態、CSS 動畫、canvas 動畫） | 0.6% | 最多 4 個同時在畫面內，約 21 秒 |
| 10 張 1080×1920 圖片 | 0.6% | |
| 5 張各 1,200 個節點的 SVG | 0.7% | rAF 掉幀 1.1% → 2.3%，凍結 3 次 |

只量了捲動，沒量 iframe 載入的成本。

第一版把這些元素放在畫面上方 2,300 px 以外，數字全部一樣，是假的。量畫面外的東西什麼都量不到，要先確認進了畫面。

打開 34 則、約 3,900 節點的對話：270–336 ms（5 次）。

真實對話（GPT 6.1 Sol，各一次）：天氣 17.5%、陽明山 18.8%、表格 57.3%。比例高是因為畫面大多靜止，和稀疏更新同一個現象，不能和 `stream` 比。陽明山那題有 2 幀超過 100 ms。

再跑 5 題（陽明山 3 次、天氣、咖啡店），記錄 rAF 間隔、Long Animation Frame 和當下新增的節點：沒有一幀超過 100 ms，最長 77 ms。超過 33 ms 的幀每題 0–5 幀，但 rAF 只有一次超過 33 ms（42 ms，按下送出那刻），Long Animation Frame 是 0，所以這些長幀不是主執行緒造成的，也對不上卡片掛上的時刻。那 2 幀沒有重現，原因不明。

## 量測時踩到的

- `test/device/page.ts` 找的是 `localhost` 的頁面，開著本機網頁的 Bot 分頁時可能接錯頁面，量之前先關掉。
- 單輪結果常被下一輪推翻，下結論前要重跑，前後各量一次基準。
