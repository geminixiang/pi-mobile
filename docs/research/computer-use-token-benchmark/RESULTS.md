# 實際 GUI 任務：結果

2026-10-24。**已完成 30 次實際任務嘗試，不是 schema 推估，也不是 action replay。**

## 結論

在同一個 `gpt-6.1-sol` 模型路由、相同 agent loop、三個自製多步驟 GUI workflow、每題每組五次的條件下：

- pi-mobile MCP 累計 **1,484,263 tokens**，computer-use-mcp 1.8.0 累計 **4,812,272 tokens**，少 **69.2%**。包含快取輸入與輸出。
- 成功率 **14/15 vs 15/15**。pi-mobile 有一次漏填訂單備註卻宣稱成功，按失敗計算，沒有補跑或刪除。
- 排除整組不匹配成功的配對，只看**雙方都成功的 14 組**：總 tokens 少 **68.4%**，輸入 tokens 少 **68.5%**。這是有條件的成功樣本分析，不代替全樣本成功率。
- **未快取輸入只少 30.0%，不能宣稱帳單省 69%。** 本實驗沒有用供應商帳單或單價計算費用。

## 任務確實做了什麼

1. **訂單修改**：篩選待處理、跨頁辨識名稱相似的客戶、填四個欄位、勾核對、在第二頁輸入訂單編號確認儲存。
2. **三階段報銷**：改用途／部門／申請人，保留日期；改兩筆金額、刪一列、增一列；核對總額、確認單據並送出。
3. **跨頁批次任務**：篩選 Pilot、跨頁選五筆、批次更新狀態，再修改指定任務的負責人／優先度／日期，保留 Core 全部資料。

模型真正透過 MCP 截圖、滑鼠、鍵盤完成。治具是本機隔離網頁與合成資料，不是真實商業系統或帳號。每次結束後比較**整份資料狀態**，連非目標紀錄也必須不變；不以模型自述完成代替判分。

**你的版本回傳的截圖反而更多，總 token 卻更少。** 最明顯的可觀察差異是模型回應次數少了 64.6%：原生批次動作加上操作後自動附圖，減少了重新讀取累積上下文的回合。不過這不是單因素消融試驗，不能聲稱已把所有節省量歸因於其中某一項；兩邊 schema、圖片尺寸與工具語意都不同。

## 方法與限制

- 詳細設定、任務提示、順序、停止規則見 [PROTOCOL.md](PROTOCOL.md)。固定版本與本地 schema 結果見 [README.md](README.md)。
- 使用本機 CLIProxyAPI 的 `gpt-6.1-sol` 路由、low reasoning、OpenAI chat/completions。名稱由 API 回報；沒有獨立驗證供應商後端模型身分，不能宣稱結果代表所有 GPT 或 Claude。
- 是單模型、三個自製合成 workflow、每格五次的小型實驗，不是通用 computer-use 能力排名。任務含有大量可批次的表單操作。
- 對方仍使用其原始 schema；相同 agent loop **允許兩邊同輪多個 tool calls**，沒有刻意禁止對方批次。但是沒有提供 code mode。若另加能把對方動作串成腳本的 agent harness，差距可能不同。
- 沒有把自製 MCP 直接嵌入模型 harness、卻讓對方走額外包裝：兩邊同樣經 MCP stdio over host WebSocket。
- 保留六次初步實跑和 24 次追加測量；初步上限 40 回應／300 秒，追加前提高到 80／480。全部都正常結束，無上限截斷或 API 錯誤。六次初步實跑不是看結果挑出的成功樣本。
- 未控制供應商快取、系統時鐘和游標的完全一致。交錯執行降低單一時間段影響；速度只作次要描述。
- JPEG/PNG 位元組數不是 vision token 數。沒有以檔案壓縮率估算 token，也沒有提供成本美元數。
- 原始 usage、工具呼叫、結果文字、完整實際／預期 state 與最終截圖已保留；模型 reasoning_content 與 opaque signatures 已移除。每步圖片僅存大小／hash，不包含完整圖片 replay。
- 手機 app 的另外兩次預檢因 code mode 丟掉 MCP 圖片而失敗，不納入這 30 次。這批因此是 **MCP 的直接 agent-loop 比較，不是手機 app 的端到端比較**。
