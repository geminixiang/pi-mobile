# 評估：computer-use-mcp 能不能當 pi mobile 內建的畫面操控

2026-10-23。評估對象是 [domdomegg/computer-use-mcp](https://github.com/domdomegg/computer-use-mcp) 1.8.0。用 `computer://` 網址在 Mac mini 上執行（`npx -y computer-use-mcp@1.8.0`，見 `src/agent/sandbox/host.ts` 的 `HostStdioTransport`），從 S24 讓 Bot 操作。評估的目的有兩個：決定它夠不夠格成為內建的 MCP，以及要不要自己寫一套。

## 它提供什麼

只有一個工具 `computer`，用 `action` 切換 11 種動作：
- 看：`get_screenshot`、`get_cursor_position`。
- 滑鼠：`mouse_move`、`left_click`、`right_click`、`middle_click`、`double_click`、`left_click_drag`、`scroll`。
- 鍵盤：`key`、`type`。

細節：
- 截圖縮到 1464×823，並畫上紅色十字標出游標；模型給的座標會換算回螢幕的實際座標。
- 標示成 `readOnlyHint: false`，連截圖也是，所以在 pi mobile 裡**每個動作都要核准**。
- 底層用 nut.js。macOS 26 上它的截圖會失敗，改走 `screencapture`；Linux 打字用 xdotool。
- 工具定義（`tools/list`）：**4,108 字元，約 1,000 tokens**，其中說明 2,127 字元、參數 1,796 字元。這組工具是需要時才載入，每段對話第一次用時由 `tool_search` 載入。

## 怎麼量

- **三個只能靠畫面完成的工作**：每題都加上「只能用電腦操控（看畫面、點擊、打字）完成，不要用指令或腳本」。
  - **calc**：在計算機上算 (37+45)×12。
  - **settings**：打開系統設定 › 一般 › 關於本機，讀出晶片型號。
  - **textedit**：在文字編輯開一份新文件，打上「pi eval 測試」，讀出視窗標題，不存檔。
- **環境**：
  - 每次都用全新的 Bot，直接操作 Mac mini（M4，macOS 27），並開啟「電腦操控」。
  - 兩個模型各跑兩次：GPT 6.1 Sol（思考低），Claude Opus 5.5（思考低）。
  - 核准一律按允許。
- **紀錄**：用 `.pi/skills/device-testing/scripts/trace.js` 記下秒數、模型呼叫次數、截圖和動作的次數、核准次數，以及 tokens。
- **對照組**：同樣三題，拿掉上面那句限制（GPT，各一次），看 Bot 用指令會怎麼做。

對照組（GPT，不限制方法）：
- **calc**：38 秒，用 osascript 操作計算機再截圖確認，0 次核准。

- **textedit**：逾時。osascript 要控制「文字編輯」，macOS 又跳出一個新的自動化權限詢問；每個 app 第一次被控制都會問一次。

## 看到的問題

1. **核准太多次**：一個工作要按 4–22 次「允許」，連截圖也要。Claude 會在同一輪同時要求好幾個動作，所以次數更多。這是最大的問題，這樣沒辦法日常使用。
2. **截圖很慢**：每張 2–7 秒。原因是 macOS 26 之後 nut.js 截不了圖，改呼叫 `screencapture` 存成 PNG 再讀回來重新編碼。三題裡，畫面工具本身的時間佔了 14–56 秒。
3. **每一步都要來回一次**：每個動作都是一次模型呼叫，動作之後模型還要另外要一張截圖才知道結果，所以呼叫次數大約是動作數的兩倍。
4. **一張截圖約 1,500 tokens**：GPT 每次截圖後，輸入大約增加 1.5k tokens。一個工作的輸入總量是 66k–373k tokens（大部分有快取）。
5. **會失控**：GPT 做 textedit 時有一次花了 24 次呼叫、22 次核准、170 秒，一路在試錯；另一次只要 6 次呼叫。
6. **要有 Node**：靠 `npx` 執行，電腦上沒有 Node 就跑不起來。另外它用的是 login shell 的 Node（Homebrew），不是使用者 nvm 裡的那個。
7. **評估本身的干擾**：計算機和文字編輯會保留上一次的畫面和文件，所以 Claude 有兩次看到「計算機一打開就已經是這個算式」。結果仍然正確，但下一輪評估要在每題之間清乾淨。

## 也順便修掉的 bug

同一輪裡有兩個工具同時要求核准時，第二個對話框會蓋掉第一個，被蓋掉的工具就永遠等不到回答。Claude 的六次裡有四次因此卡到 600 秒。當時改成排隊（`697ca43`）；之後整個核准機制都拿掉了，見下面。

## 判斷

**後續（同一天）**：pi mobile 拿掉了所有核准，問題 1 已經不存在；下面的判斷和標準照當時的數據寫，自己寫的版本仍以呼叫次數、秒數和不需要 Node 為準。

**computer-use-mcp 現在不夠格成為內建。**它能用，三題也都答對，但核准次數、截圖速度、Node 依賴這三點都過不了日常使用的門檻。目前維持「使用者自己在連接的服務裡加入」的狀態。

**值得自己寫一套**，做成 `pi-mobile` 電腦端的一部分（Go，不需要 Node）。照這次的數據，該做的事：

| 做法 | 要解決的問題 | 預期效果 |
|---|---|---|
| 截圖獨立成唯讀的工具，動作另一個工具 | 1 | 截圖不用核准，核准次數少一半以上 |
| 整段工作核准一次（例如「讓 Bot 操控這台電腦 10 分鐘」） | 1 | 每個工作只核准一次 |
| 每個動作做完自動附上新的截圖 | 3 | 模型呼叫次數大約減半 |
| 一次可以送出多個動作（點擊、打字、按鍵、等待） | 3、5 | 簡單的步驟一輪做完 |
| 直接截成縮小的 JPEG，不經過 PNG 存檔再讀回 | 2、4 | 每張不到 1 秒，tokens 更少 |
| 同時回傳文字資訊：前景 app、視窗標題、視窗清單 | 4、5 | 很多時候不必靠看圖判斷 |
| 用 Go 呼叫 CoreGraphics（macOS）和 X11／xdotool（Linux） | 6 | 不需要 Node |

自己寫的版本，用同樣三題和同樣的量法評估，至少要做到：
- 每題核准 1 次。
- 每題的模型呼叫和秒數，都比上表少一半。
- 不需要 Node。

做到了才把它內建進 pi mobile。
