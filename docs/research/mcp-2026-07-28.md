# MCP 2026-07-28：規格重點，以及我們的落差

2026-10-23。MCP 沒有「2.0」，版本號是日期，目前最新的是 **2026-07-28**，取代 2025-11-25。這份整理新版規格裡跟 pi-mobile 有關的部分，再對照我們的 client（`@earendil-works/pi-mcp` 1.4.0）和我們自己的 server（`host/computer.go`）。規格出處是 [modelcontextprotocol/modelcontextprotocol](https://github.com/modelcontextprotocol/modelcontextprotocol) 的 `docs/specification/2026-07-28/`，下面用相對路徑標出處。

## 1. 協定變成無狀態

- **拿掉握手**：沒有 `initialize`、`notifications/initialized`。每個請求自己在 `params._meta` 帶：
  - `io.modelcontextprotocol/protocolVersion`、`io.modelcontextprotocol/clientCapabilities`（必填）；
  - `io.modelcontextprotocol/clientInfo`（SHOULD）。
  
  server 在每個結果的 `_meta` 帶 `io.modelcontextprotocol/serverInfo`（SHOULD）。版本不合時回 `UnsupportedProtocolVersionError`（`changelog.mdx` 主要變更第 2 點）。
- **拿掉 session**：`Mcp-Session-Id` 沒了；`tools/list` 這類列表不能因連線而不同（主要變更第 1 點）。
- **規格的原話**（`basic/index.mdx` § Statelessness）：
  - server 不能靠同一條連線上之前的請求建立脈絡（MUST NOT）。
  - server 要能處理來自多個任務、對話的請求（SHOULD）。
  - **client 不該用一個任務或對話當 stdio 程序的生命週期**（SHOULD NOT）。
  - 要跨請求保留的狀態，必須用 client 每次帶上的明確識別碼（MUST）。
  - 附註說得更直白：**stdio 程序不是對話，也不是 session**，server 不能把連線或程序的身分當成對話的延續。
- **要有狀態，就用 handle**（`server/tools.mdx` § Stateful Tools，非規範性）：例如購物車、開著的瀏覽器、資料庫交易。由建立用的工具回傳一個 handle（例：`basket_id`），之後的呼叫把它當一般參數帶上，server 用它查狀態。

## 2. `server/discover` 和新舊版相容

- server **必須**實作 `server/discover`，回傳 `supportedVersions`、`capabilities`、`serverInfo`、`instructions`，可以帶快取提示（`server/discover.mdx`）。client 可以不先呼叫。
- **stdio 上怎麼判斷新舊**（`basic/transports/stdio.mdx` § Backward Compatibility）：兩版都支援的 client 應該先送 `server/discover`：
  - 回 `DiscoverResult`：新版 server，從 `supportedVersions` 選一個。
  - 回新版的錯誤（如 `UnsupportedProtocolVersionError`）：新版但版本不合，改用它列出的版本，**不要**退回 `initialize`。
  - 其他錯誤或逾時：舊版 server，退回 `initialize`。判斷不能只看某一個錯誤碼。
- **相容矩陣**（`basic/versioning.mdx`）：

| client | server | 結果 |
|---|---|---|
| 新版 | 舊版 | 失敗。stdio 上應先送 `server/discover`，失敗得乾脆，再告訴使用者 |
| 兩版都支援 | 新版或舊版 | 都可以 |
| 舊版 | 新版 | **失敗**。舊版 client 沒有往新版切換的機制 |
| 舊版 | 兩版都支援 | 可以 |

- **只支援新版的 server**，收到 `initialize` 時，錯誤裡應該列出自己支援的版本（SHOULD）。

## 3. 傳輸

**stdio**（`basic/transports/stdio.mdx`）
- 一行一則訊息，不能內嵌換行；stdout 只能寫 MCP 訊息，log 寫 stderr；server 不能在 stdout 寫 JSON-RPC 的*請求*。
- **關閉流程**：client 先關掉 stdin，等 server 結束；等不到再強制結束（POSIX 上從 SIGTERM 升級到 SIGKILL）。server 讀到 EOF 應該盡快結束，這是唯一可攜的正常關閉訊號。
- server 意外結束，client 應該重新啟動它；新版無狀態，進行中的請求就丟掉重送。
- **取消**：stdio 沒有每個請求的串流可以關，client 必須送 `notifications/cancelled`（`basic/patterns/cancellation.mdx`）。

**Streamable HTTP**（`basic/transports/streamable-http.mdx`）
- 每則訊息一個 POST，回 JSON 或只屬於那個請求的 SSE。
- 必要 header：`MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name`；跟內容對不上時回 400 和 `HeaderMismatch`。
- 拿掉了 GET 串流和 `Last-Event-ID` 斷線續傳：串流斷了，請求就沒了，要用新的 request id 重送。
- 變更通知改成 `subscriptions/listen`，一個長時間保持的 POST 回應串流（`basic/patterns/subscriptions.mdx`）。
- server 必須檢查 `Origin`；在本機執行時應該只綁 localhost。

## 4. 工具、結果、其他

- **`resultType`**：每個結果都要帶，一般是 `"complete"`；client 遇到沒帶的舊版 server，要當成 `"complete"`（主要變更第 8 點）。
- **多次來回（MRTR）**：server 要反問時，回 `resultType: "input_required"` 和 `inputRequests`，client 補上 `inputResponses` 重送原請求，取代 server 主動發的 elicitation、sampling、roots 請求（主要變更第 7 點、`basic/patterns/mrtr.mdx`）。
- **工具 schema**：`inputSchema`、`outputSchema` 可以用任何 JSON Schema 2020-12 關鍵字；`structuredContent` 可以是任何 JSON 值。
- **annotations 不可信**：client 必須把工具的 annotations 當成不可信，除非來自可信的 server（`server/tools.mdx` 第 305 行）。
- **工具順序**：`tools/list` 應該用固定順序回傳，方便 client 快取，也提高 LLM 提示快取的命中率。
- **列表快取**：`tools/list` 等列表和 `resources/read` 必須帶 `ttlMs`、`cacheScope`（次要變更第 5 點）。
- **拿掉的**：`ping`、`logging/setLevel`、`notifications/roots/list_changed`；log 等級改成每個請求在 `_meta` 指定。
- **改成 extension**：Tasks 移到 `io.modelcontextprotocol/tasks`。
- **棄用**（至少保留 12 個月）：
  - Roots、Sampling、Logging，以及舊的 HTTP+SSE 傳輸。
  - **Dynamic Client Registration**，改推 Client ID Metadata Documents（CIMD）。
- **授權**：
  - client 必須核對授權回應裡的 `iss`（RFC 9207）。
  - 動態註冊時必須帶 `application_type`。
  - 憑證要依 issuer 存放，換了授權伺服器就要重新註冊。

## 5. 我們的 client：pi-mcp 1.4.0

讀的是 `~/github/pi/packages/mcp/src`：

| 項目 | pi-mcp 1.4.0 | 新版規格 |
|---|---|---|
| 版本 | `LATEST_PROTOCOL_VERSION = "2025-11-25"`，最舊支援到 2024-11-05（`protocol/types.ts:4–9`） | 2026-07-28 |
| 握手 | 一定先送 `initialize`、`notifications/initialized`（`client.ts:221–243`） | 拿掉；應先送 `server/discover` 判斷新舊 |
| `server/discover`、`_meta` 版本 | 沒有 | 必要 |
| HTTP session | 送 `Mcp-Session-Id`、`MCP-Protocol-Version`（`streamable-http.ts:328–329`）；初始化後開 GET 串流（`:248`、`:422`）；用 `Last-Event-ID` 續傳（`:379`） | 都拿掉了；改 `Mcp-Method`、`Mcp-Name`、`subscriptions/listen` |
| `ping`、`roots/list` | client 會回應（`client.ts:175–179`） | 拿掉、棄用 |
| 取消 | 有 `notifications/cancelled`（`client.ts:570`） | 一樣 |
| stdio 關閉 | 關 stdin，等 500 ms 再 SIGTERM，共 2 秒（`transports/stdio.ts:8–10`） | 符合 |
| OAuth | 有 `iss` 驗證（`oauth/flow.ts:74`、`:385`）、`application_type`（`:110`、`:266`）；讀得到 `client_id_metadata_document_supported`，但還是用動態註冊 | 符合大部分；CIMD 還沒用 |

**結論：pi-mcp 是「只會舊版」的 client。**照相容矩陣，它可以接舊版和兩版都支援的 server，**接不上只支援新版的 server**，而且不會失敗得很乾脆：送出 `initialize` 後，等到的是一個實作自訂的錯誤。我們用的服務（Cloudflare、Notion 等）現在都還接受舊版，所以還沒出事。

**我們這邊用到 pi-mcp 的地方**
- `src/agent/mcp.ts`：HTTP 服務，`openGetStream: false`（本來就不用 GET 串流）、動態註冊、固定的本機轉址網址。
- `src/agent/tools/computer.ts` 和 `src/agent/sandbox/host.ts` 的 `HostStdioTransport`：每台電腦一個長期的 stdio 連線，跑 `pi-mobile mcp computer`。

## 6. 我們的 server：`pi-mobile mcp computer`

| 現在 | 新版規格 | 要改的 |
|---|---|---|
| 只回應 `initialize`；`tools/call` 不看 `_meta` | 必須有 `server/discover`，每個請求讀 `_meta` 的版本 | 同時支援兩版：加 `server/discover`，讀 `_meta`，保留 `initialize` 給 pi-mcp |
| 結果沒有 `resultType` | 必填 | 加 `"resultType": "complete"` |
| `tools/list` 沒有 `ttlMs`、`cacheScope` | 必填 | 加上（工具不會變，`ttlMs` 可以很長） |
| 有 `ping` | 新版拿掉 | 保留給舊版 client 無妨 |
| **收拾 app 的範圍是「這個程序」**：一個程序一個 session，閒置 2 分鐘、stdin 結束或 SIGTERM 時收掉開過的 app | **違反「程序不是 session」**：同一台電腦上兩個 Bot 共用一個程序，會把彼此開的 app 算在一起，也會被對方的閒置計時延後或提早收掉 | 改用明確的 handle：由手機端的包裝（`computer.ts`）幫每個 Bot 的對話帶一個 `session` 參數，模型不用管；server 依 handle 記錄各自開的 app、各自計時 |
| stdin 結束就收掉、結束程序 | 規格要 server 讀到 EOF 就盡快結束 | 已經符合 |

## 對 pi-mobile 的結論

1. **自己的 server 先改成兩版都支援**，並加上 `resultType`、`ttlMs`、`cacheScope`。這是我們自己能控制的，改動小。
2. **畫面操控的 session 改用明確的 handle**，每個 Bot 的對話各自一個，避免兩個 Bot 互相收掉對方的 app。手機端的包裝自動帶上，模型看不到。
3. **pi-mcp 要支援新版**：先送 `server/discover` 判斷新舊、每個請求帶 `_meta`、HTTP 帶 `Mcp-Method`／`Mcp-Name`、拿掉 session 和 GET 串流、處理 `resultType` 和 `input_required`。這是上游的事（pi repo），等它或去提 PR。在那之前，遇到只支援新版的服務會接不上，錯誤訊息也不清楚。
4. **市集加入新服務前，多驗一項**：它是否還接受舊版的 `initialize`。
5. **OAuth 之後改用 CIMD**：動態註冊已經棄用，至少還保留 12 個月，不急。
