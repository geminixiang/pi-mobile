# 使用者分享的參考與學到的事

使用者看到好東西就會分享過來。這份記下每一個參考：從中學到什麼、對 pi mobile 的決定是什麼、做到哪裡。之後做設計或功能前先讀這份，新的參考也記在這裡。

## 原則：先定核心目的

2026-11-13，使用者看了 iPad 工作台的第一個方向後說：「這個工作台設計是要成為真正的生產力工具的，而不是單純把東西放上去而已，記住，你做事情是要有核心目的的。」

所以做任何畫面或功能之前，先寫下它的核心目的：它讓使用者完成什麼事、少做哪幾步。每個元素都要為這個目的服務。只是把資訊擺出來的東西，要嘛拿掉，要嘛收到點開才看到。做完之後量一次，例如從 Bot 交出草稿到使用者核准，要點幾下、花幾秒。

學到的參考，也照這個標準來取捨：看這個做法能不能讓使用者更快把事做完，而不是它看起來新。

## 維護這個產品（2026-11-13，從 poteto 的演講對照現況）

現況（跑 `grep` 數的）：`src/` 裡 `useEffect` 69 個（`src/app` 59 個）、`setTimeout` 21 個、`setInterval` 7 個、`requestAnimationFrame` 5 個；`// why:` 27 個；AGENTS.md 的規則表 39 列；4 週 878 個 commit、4 個 revert。

依優先順序：

1. **容易誤用的東西收到一個地方。** 每個 `useEffect` 和計時器，判斷是不是在補架構的洞：同步外部狀態的，改成 `useSyncExternalStore` 或資料層；「等一下再做」的，找出它在等什麼事件。收斂後用 code-rules 限制只有少數模組能用，錯誤訊息寫出改用什麼。
2. **隱性狀態機變成顯式的。** 2026-11-10 已經盤點出約 25 處（電腦連線 `resumable-socket.ts`、`phone-connection.ts`、`host/held.go` 最急）。改成判別聯集，關鍵的跨裝置流程（斷線、重接、恰好一次送達）用 TLA+ 或屬性測試驗證；待辦 #14 那個偶發失敗的測試（第 11 行遺失、第 12 行重複）就是這類流程出錯的徵兆。
3. **功能地圖。** 一份從使用者角度列出所有畫面和功能的地圖，每一項有正式名稱（右側欄、連線圖、能做什麼、工作台、舞台、托盤…）和對應的元件，`test/` 檢查名稱和程式對得上。之後使用者說「那個左邊的」，agent 不用猜。
4. **驗證證據進 commit。** UI 改動附改前改後截圖（`test/device/` 已有工具），效能改動附 `test/perf/run.ts` 的數字。派出去的 agent 已經這樣交報告，變成固定格式。
5. **清掉舊寫法。** DESIGN.md 列的「要淘汰的舊寫法」（`.group`、`.menu` 框、列表列裡的按鈕）一次清完，不要讓下一個 agent 照抄；清完加檢查。
