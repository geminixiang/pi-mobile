# 手機畫面：token 和速度的量測計畫

2026-10-25 定；第一輪（清單 vs 截圖）同一天跑完，結果在最後。目的：找出 `read_phone_screen`／`use_phone_screen` 在不同工作上花多少 token、多少時間，哪些改動能讓同樣的工作用更少的呼叫、更少的 token 做完，而且不降低成功率。背景見 [phone-screen.md](phone-screen.md)。

## 第一輪看到、要驗證的事

- **模型多半從 codemode 呼叫 `use_phone_screen`**（`text(await tools.use_phone_screen(...))`），這時它只拿到文字清單，看不到截圖；只有直接呼叫 `read_phone_screen` 才看到圖。幾個工作只靠清單就做完了。要量：清單夠用的比例、沒有圖時失敗在哪。
- **一張 540 寬的 JPEG 約 50 KB**；清單通常 1–3 KB。圖的 token 由模型供應商的計算決定，不能從檔案大小推算，要看 usage。
- **選填欄位被填滿**：`open` 帶著 `x: 0, y: 0, direction, ms: 1, text: ""`。輸出 token 小，但每一步都有。
- **捲動後等畫面安靜常等到上限**（設定 app 約 2.9 秒）：內容一直在變（動畫、列表載入）。
- **一個工作的呼叫數**：計算機 3 次工具呼叫、設定 7 次、刪筆記 10 次。

## 工作

每題都只能靠畫面完成，問法不提工具；固定起點（從 pi 開始，目標 app 先 force-stop），結束後檢查實際狀態，不只相信 Bot 說的。

| 類型 | 題目 | 檢查 |
|---|---|---|
| 讀，一個畫面 | 時鐘 app 裡有哪些鬧鐘、哪些開著 | 和 `dumpsys alarm`／畫面對照 |
| 讀，要導覽 | 設定裡的 One UI 版本 | 8.5 |
| 讀，要捲動 | 設定 › 應用程式裡，哪三個 app 佔最多空間 | 和設定畫面對照 |
| 算 | 用計算機算 (37+45)×12 | 984 |
| 寫，打字 | 三星筆記新增「pi 測試」，內容一句話 | 筆記存在、內容一字不差 |
| 寫，多步 | 時鐘 app 新增明天 7:30 的鬧鐘，標籤「pi 測試」（不用 `set_alarm`：題目說「在時鐘 app 裡」） | 鬧鐘存在，測完刪掉 |
| 刪 | 刪掉「pi 測試」筆記，垃圾桶裡的也清掉 | 只少那一則 |
| 跨 app | 把計算機的結果貼到三星筆記 | 筆記內容是 984 |

## 記錄

`trace.js`（`device-testing`）的 SUMMARY：秒數、模型呼叫數、未快取和快取的輸入 tokens、輸出 tokens；另外記：

- 成功與否（看實際狀態）。
- `read_phone_screen` 和 `use_phone_screen` 各呼叫幾次、幾次從 codemode、幾次帶圖。
- 每次工具的時間（plugin 自己的時間，`phone-screen.js` 可以單獨量）。

每題每個版本至少跑 3 次（模型每次走的路不同），報中位數和範圍；失敗的不重跑成成功，也不拿「失敗得快」當省 token。

## 要比較的改動

一次只改一件，前後在 S24、同一個模型、同一組題目上比：

1. **清單和截圖的取捨**：只給清單、清單加截圖、截圖預設不給但可以要（`read_phone_screen` 加參數）。
2. **截圖大小**：寬 540、720、360；JPEG 品質。
3. **用元件編號點**：`tap {element: 12}` 代替座標，清單可以省掉座標。
4. **清單瘦身**：去掉重複的外層按鈕（「天氣與時鐘 · …」和裡面那一個）、沒有文字的 `list`、`disabled` 的元件。
5. **等待**：安靜門檻 350 ms 和上限 2.5 秒；捲動用目標元件出現就停。
6. **工具說明**：要模型直接呼叫（看得到圖）還是從 codemode（省一次來回），說明各寫一版比較。
7. **模型**：GPT 6.1 Sol、Claude Opus 5.5、一個便宜的模型（例如 Haiku 5.5），看清單夠不夠讓小模型做完。

## 決定的標準

成功率不降；同一題的中位數 tokens 或秒數少 15% 以上才算改善。結果和決定寫回 [phone-screen.md](phone-screen.md) 和 `docs/tools.md` 的紀錄。

## 第一輪：清單加截圖 vs 只有清單（2026-10-25）

**設定**：S24，`main` 的 `06c96c2`。只改 `phone-screen.ts`：「只有清單」不附截圖，說明裡的「a screenshot」拿掉、座標改叫 points（原生端照樣截圖，所以時間不受影響）。GPT 6.1 Sol（新 Bot 的預設），每題 3 次，五題輪流，每次都是新的暫時 Bot、目標 app 先 force-stop（計算機另外 `pm clear`，否則會留著上次的 984）。執行：`docs/research/phone-screen-benchmark/run.mjs <serial> <variant> 3`（原始 trace 在 `runs/`，含使用者的鬧鐘和 app 名稱，不進 repo）。

輸入 tokens 是 API 回報的 input 加 cache read。

**看到的**：

- 這一輪模型都直接呼叫工具（有看到圖），不像第一次實測多半從 codemode 呼叫。同一個模型、同樣的說明，走法會變。
- 每張截圖大約 1,000–1,500 輸入 tokens；要捲動、看很多畫面的工作，截圖累積得最快（儲存空間那題 12 張）。
- 只有清單時，5 題裡 4 題的中位數少 19–59%，鬧鐘多 8%（有一次多捲了幾次）。秒數合計差不多：模型呼叫次數沒有變少，省下的是每次帶的圖。
- 唯一的失敗在「清單＋截圖」：鬧鐘第 3 次，模型沒有載入畫面工具，直接說沒有工具能讀鬧鐘。跟有沒有截圖無關，是載入工具的判斷；說明要讓模型知道「讀其他 app 的內容」就是用這組工具。
- 實際狀態都對過：6 則筆記內容一字不差（測完由 Bot 刪掉並清空垃圾桶，筆記數回到 4）；儲存空間三次的答案相同（Edge Gallery 7.08 GB），與設定畫面一致。
- 測試中 Bot 在別的 app 時，pi 在背景偶爾整個停住（一次卡了 9 分鐘，叫回前景就繼續）。量測時用一個小腳本，在 AgentService 不在時把 pi 叫回前景；這本身是要查的問題：Bot 正在操作其他 app 時，pi 必須在背景繼續跑。

**判斷**：這五題只靠清單就夠，token 明顯少，成功率沒降，達到 15% 的標準。但這五題的畫面都有文字標籤；沒有標籤的圖示、圖片內容、地圖、遊戲只有截圖看得到。所以下一個版本是「預設只給清單，`read_phone_screen` 可以要截圖」，量的時候加一題要看圖的（例如相簿最新一張照片裡有什麼），確定模型需要時會要。
